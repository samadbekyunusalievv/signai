SignAI Technical Architecture

Camera → ASL recognition → LLM → 3D signing avatar. End-to-end design for the prototype and a possible path beyond it.

The whole loop runs in the browser (with optional server-side LLM). The user signs in front of a webcam, sees a transcribed message in chat, gets an AI response, and watches a 3D avatar perform that response in ASL.

2Stage 1 — Sign Recognition

The input pipeline turns raw camera frames into discrete sign tokens.

2.1 Hand tracking

MediaPipe Hands runs in-browser via WebAssembly (or GPU via WebGPU on supported devices). It outputs 21 3D landmarks per hand at 30+ fps, with built-in handedness classification.

// Per-frame output
{
  multiHandLandmarks: [
    [{x, y, z}, ...21 points],   // hand 1
    [{x, y, z}, ...21 points],   // hand 2 (optional)
  ],
  multiHandedness: [{label: "Right", score: 0.99}, ...]
}

2.2 Classifier — three tiers

VersionApproachVocabularyUse case
V0 (this prototype)Hand-coded heuristics over landmark geometry~8 signsDemo, prove the loop
V1MLP / Random Forest on landmark vector + temporal smoothing50–100 static signs + ASL alphabetSchools, fingerspelling
V2Transformer / 3D-CNN on landmark sequences (e.g. SignBERT-style)1000+ continuous signsReal conversation

2.3 Why heuristics first

For the prototype, hand-rolled rules ("thumb out + index extended + pinky extended ⇒ I-LOVE-YOU") demo cleanly without training a model live. They give us an honest, runnable loop today; the same architecture swaps cleanly to ML weights later.

2.4 Temporal stability

Static-frame classification is jittery. We hold a recognized sign for 600 ms before emitting it, and apply a 1500 ms cooldown to prevent the same sign repeating from a single gesture. In V1, swap this for a sliding-window classifier with hysteresis.

3Stage 2 — Conversational AI

Once the user's signed input is text, this is a normal LLM round-trip — but with one twist: we ask the model to return both the natural-language reply and an ASL gloss sequence (the canonical word-by-word ASL token list).

// LLM prompt template (V1)
SYSTEM: You are SignAI, an assistant for Deaf signing users.
Reply in two parts:
  1. Natural English reply
  2. ASL-GLOSS TOKENS IN UPPERCASE
Use ASL grammar conventions (topic-comment, time markers,
classifiers). Keep replies short — they will be signed.

USER: HELLO HOW YOU?
ASSISTANT:
  <text>Hi there — how are you today?</text>
  <gloss>HELLO YOU HOW NOW?</gloss>

Model Claude Haiku or GPT-4o-mini work for V1 — both are fast enough for sub-second turn times. Latency target <1.2 s end-to-end (sign captured → avatar starts moving).

4Stage 3 — Avatar Output (Text → Sign)

The hardest part of the long-term roadmap. Going from English → ASL animation is not a literal word-for-word mapping — ASL has its own grammar (topic-comment word order, non-manual markers, classifiers, spatial referencing).

V0 (this prototype)

Each gloss token maps to a hard-coded keyframe sequence in Three.js. The animation engine queues sequences and lerps between them. Works for a fixed vocabulary, demos beautifully.

V1+ (production path)

A sign library built from motion-capture data (MoCap suits or pose-estimated from videos of ASL signers). Each library entry is a parametric animation with timing, intensity, and facial expression channels. The avatar renderer concatenates them.

Avatar rig

V0 uses a hand-built humanoid (head, torso, 2-segment arms, jointed hands). V1 swaps in a rigged glTF character (Mixamo, Ready Player Me, or a deaf-community-designed avatar) with full finger and face bones.

Non-manual markers

Eyebrows, head tilt, mouth shape carry grammatical meaning in ASL (questions, negation, conditionals). V2 needs facial blend-shapes driven by the gloss tokens — currently a known gap in most signing avatars.

6Data & Training Plan

The defensible asset over time is the dataset. The sign-recognition CNN is only as good as its training data, and most public ASL datasets are small.

  • Public starter datasets — WLASL (2000 signs, ~12k videos), MS-ASL, How2Sign, ASL-100-RGBD.
  • Crowdsourced expansion — opt-in "teach SignAI" mode where users record themselves signing labeled words; pays back into the model with consent.
  • Partner collection — collaborate with Gallaudet, RIT/NTID, and deaf-led organizations for high-quality, signer-validated data.
  • Synthetic augmentation — pose-perturbation and 3D rendering of avatar variations to widen the distribution.

7Privacy & Ethics

  • On-device first. Hand tracking runs in the browser. The raw camera feed never leaves the user's machine.
  • Server only sees text. Only the recognized text (or its embedding) goes to the LLM — same privacy posture as a normal chatbot.
  • Deaf-led product decisions. Every sign-library entry, avatar design, and grammar rule is reviewed by deaf signers, not invented by hearing engineers.
  • Avatar consent. If we mocap real signers for the library, they're paid, credited, and retain rights over their likeness.
  • No facial recognition. We don't store identifiable face data; only landmark vectors stripped of identity.

9Honest Risks

  • ASL is hard. Continuous, conversational ASL recognition is an open research problem. We will be wrong sometimes; the product needs gentle correction UX (suggest edits, fingerspell fallback).
  • Avatar acceptance. Some deaf communities are wary of AI avatars replacing human interpreters. We position SignAI as a complement to interpreters (everyday, low-stakes, on-demand) — not a replacement for high-stakes settings (medical, legal).
  • Data scarcity. ASL-signer-validated data at the scale of English text is decades away. We compensate with strong heuristics, fingerspelling fallback, and iterative learning from user corrections.
  • Latency. Sub-second feels native; over 2 seconds breaks conversation flow. We design every layer with this budget in mind.

10What's Built Today

The app (index.html + js/) implements the full V0 loop end-to-end:

  • Live webcam → MediaPipe Hands landmarks (21 × 2 points/frame)
  • Heuristic sign classifier for: hello yes no thank-you help please i-love-you stop
  • Hold-and-cooldown temporal stability (no flicker)
  • Chat UI with user/bot turns and ASL gloss display
  • Three.js humanoid avatar with custom 2-segment arm rig and finger curl
  • Keyframed sign animations driven by the AI response gloss
  • Fully self-contained — opens in any modern browser, no backend required

That's the proof: the loop closes. Everything else is scale.
